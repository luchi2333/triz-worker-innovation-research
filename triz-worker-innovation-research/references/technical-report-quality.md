# 技术方案具体度与黑白报告验收（v2.7）

带公式和细节的方案还须执行 [技术模型与输出保真复核](model-and-output-audit.md)。具体度合格不能替代图示拓扑、单位、可辨识性、成熟度与数据输出的正确性检查。

## 1. 先形成设计，再装配报告

G3 先为每条保留路线写最小技术说明；G4 补齐可复算示例和验证协议；G5 才做正文、原理图和复核。事实、公式、参数、设计说明仍维护于 `research-record.json`；复核摘录是生成后的证据快照，放独立 `report-quality-review.json`，避免 DOCX 哈希与研究记录哈希相互依赖。

V0 表示尚未验证的具体候选设计。未知现场参数不能伪造为 M；可以提出 H 候选值、参数选择规则和假设算例。若物理关系尚不能成立，就报告哪些观测不足以及怎样判别，不能画一条箭头假装关系已经成立。研究计划可以交付，但标题、状态和结论都必须说明方案未完成。

对 primary、exploratory、alternative 及其他保留路线逐项检查；rejected 和 baseline 可以只说明淘汰依据或现有基准。采购后备标记 design_kind=procurement、diagram.kind=product-interface，按接口和适配展开，不强迫发明新硬件；纯软件分析按数据与状态转换展开，不强迫画机械剖面。混合方案分清硬件观测模型与软件推断，两部分都要解释。

## 2. 六项正文内容，不能只填字段

| 项目 | 合格内容 | 不合格替代 |
|---|---|---|
| input_output | 物理对象/数据字段、单位、测量参考点、范围/分辨率要求、输出含义；缺失、封顶、失配如何处理 | “输入信号，输出预警” |
| mechanism | 有因果解释的方程、状态关系或物理作用；变量定义、成立条件、干扰及不可辨识反例 | “采用融合算法/互谱/智能识别” |
| implementation | 元件/模块选择依据、接口、部署；或可执行伪代码、窗口/阈值选择方法；初步设计尺寸可为 H 并标来源 | “采集→分析→判定” |
| worked_example | 一组 F/M/S/H 明确的输入，中间量、单位与最终输出；正常/异常或可辨/不可辨对照；效益同样显示输入和代入 | 只列最终百分比，或把 H 结果当性能证据 |
| validation | 测试对象与仪器/数据、操作步骤、标签/真值、样本与切分方法、指标分母、基准、通过/停止规则及记录字段 | “满足冻结门槛”“按预注册口径达标”但未给口径 |
| innovation_attribution | 分开写成熟已有技术及来源、目标场景集成、候选创新、创新边界和待验证项；候选创新必须是相对现有技术的具体差异作用链/接口/协同 | 把成熟模块全部算作创新；只写“优化/改进/智能化/集成化”；把场景适配与技术创新混成一句 |

创新归属从 `research-record.json` 的 `routes[].innovation_attribution` 进入主报告正文。读者不应到附件里才能判断“哪些是成熟技术、哪些只是现场集成、哪些才是候选创新”。`mature_technology_status=identified` 时成熟技术必须给可解析来源 ID；`none_identified/unknown` 时允许无来源，但必须在正文明确写“未识别/未知”等真实状态，不能把空白误读成原创。没有新增创新时明确写“无新增创新主张”，不能为了申报效果强行制造创新点。

参数尚待校准时，给出校准数据如何取得、候选搜索范围如何推导、调参/验证隔离方式和冻结记录；不能为了填表虚构最终值。至少有一组带中间量的 H 示例，证明设计表达足够清楚，不代表证明性能。

每条保留路线必须在 `models_and_tests.protocols` 中拥有自己的协议（scope、sampling_plan、metrics、stop_rule），复核收据用 `protocol_id` 引用；不能用已淘汰路线的试验充数。未执行协议保持计划状态，不伪造 tests 或 M。尚未冻结的判据在计划中明确其确定方法与待决项；语义是否可执行仍须由读者判定。

算法示例（仅说明具体度）：假设每小时取得健康参考修正后的无量纲数列 `[10,9,8]`，三点最小二乘斜率为 `-1/h`；候选判据为连续两窗斜率低于 H 门槛 `-0.5/h` 才进入关注态，只有一窗不能触发。补给下一窗、计数更新、正常波动反例以及封顶/缺失值令窗口无效的处理。正式方案必须解释参考修正与门槛如何从目标场景确定，不能照抄此示例作推荐算法。

## 3. 完整主报告不能只满足单方案六项正文

单方案六项具体度只证明“某条路线讲清楚了”，不能替代完整研究报告。完整交付的 `report-quality-review.json.report_sections` 必须把以下正文段落绑定到当前主报告 DOCX 哈希：

| 正文锚点 | 必须回答 |
|---|---|
| scope_and_problem | 研究对象、现场问题、任务边界、已知/未知和证据边界 |
| triz_analysis | 变量方向、矛盾资格、TRIZ 方法与候选作用机制 |
| deep_research | 七轨查新覆盖、关键来源、缺口及不能声称的结论 |
| route_portfolio | 成熟基准、工程后备、高潜力探索及超系统适用性 |
| decision_and_robustness | 方案选择、最强反对意见、退出条件、移除最强支持证据后的稳健性 |
| fmea_and_validation | 危险链、控制、残余风险、验证协议与停止条件 |
| benefits | 经济计算/待数据公式和社会效益可测指标 |
| implementation_path | 下一项决定性试验、阶段闸门、采购/退出条件、边界和关键未知 |

这些锚点引用正文解释段落，不允许只指向标题或表格单元格。缺任一项时 complete 报告为 `NEEDS_REVISION`。

## 4. 原理图必须增加信息

- 电气/测量：明确电源/参考地、支路、等效元件、测量端口、电流方向、采样位置及目标量；公式中的变量在图中能找到。负荷电流与泄漏/剩余电流不能混称；电压参考不明确时不得直接声称电压电流之比可辨目标参数。
- 热/流体：可用 balance-network 表达能量/质量守恒、边界条件、阻力与流向，配合单位和量纲说明。
- 机械：剖面/接触、约束和运动/力路径；结构编号与文字对应；H 尺寸、未定材料与禁用边界醒目标出。
- 软件：状态、具体运算、输入输出及异常分支；配合数据轨迹或曲线解释为什么发生状态变化。软件流程图允许矩形和箭头，但算法名字串联不算原理解释。
- 工艺/作业：给控制点、动作条件、资源、异常返工和判定示例；采购：给目标需求与实际接口/能力适配及未覆盖项。

每张核心图都回答：相比正文的流程清单，它新增了哪个结构、变量或因果关系？图号、元件编号和变量与正文同源。F3 架构图不能充当电气等效回路或机械剖面；改成 F4 标签、增加箭头标记或装饰圆不能改变图的性质。SVG 图元统计只发现疑点，不能证明机理完整；矩形电阻符号的真实回路也不能仅因没有圆形被判无效。

## 4. 黑白三线表和图示

正文、附表、DOCX、HTML 都用白底黑字三线表：顶/底线约 1 pt，表头下线约 0.5 pt；无左右边框、竖线、彩底、逐行网格。表头可加粗并跨页重复；长表按逻辑分组，长段落移到正文。必要分组线可采用同类黑白学术风格，但须实际逐表复核；内置严格检查采用更明确的三线表子集，不暗自放行复杂自定义样式。

流程图、原理图默认白底、黑色轮廓和文字，必要浅灰填充；实线/虚线、剖面纹理、序号、符号和图例区分语义，危险用禁止线和文字，不能只靠颜色。禁用彩虹配色、渐变、阴影、装饰背景和低清截图。线条清晰与原理准确是两项要求；黑白方框图仍可能是低质量原理表达。

原始照片或实测热图确需颜色时保留原始证据，不通过改色掩盖数据；单独说明颜色含义、来源和灰度阅读方式。当前自动 style gate 对生成 SVG 采用严格单色子集，嵌入位图或未支持色值会要求修订/专门视觉复核，不能为通过检查改标图类型或修改校验器。

## 5. 读者复核和完成判定

读者先只看最终报告，回答：

1. 依照报告复算一例，从哪个输入经过哪些中间量到哪个输出？
2. 哪种具体反例会使结论失效，系统如何识别并退出？
3. 另一位工程人员明天怎样在已授权的离线/隔离环境复现最低验证？

回答必须含具体对象、关系和报告证据，不能填“已检查、符合要求”。优先让未参与撰写的读者/独立评审代理执行这一有界复核；只有单模型时，可以以最终报告为依据重新读取，进行串行读者复核（不声称上下文已隔离）并标为 `serial-reader`，不得伪称独立或专业签字。复核没有完成就留 pending，继续补报告，不要求用户为例行修订重复授权。

从 [report-quality-review-template.json](../assets/report-quality-review-template.json) 生成收据，按实际 route_id 为每条保留路线增加一份。每项 anchor 必须引用 main-report DOCX 的路径、当前 SHA256、章/页定位和实际完整段落摘录（单独摘两个词不算正文证据）。评审结果生成于 DOCX 定稿之后；定稿改变必须重新复核。正文技术内容缺失，不能仅在评审收据中补充。manifest 用 `report_quality_review` 指向收据。

`validate_deliverables.py --strict` 分列结构、计算一致性、技术内容证据、样式、工程复核。缺六项正文证据、缺真实图示说明、哈希过期或复核未完成时，complete 交付失败；degraded/blocked 可以保存阶段稿进度，但保留 NEEDS_REVISION，不能宣传成完整方案。`EVIDENCE_RECORDED` 不叫技术 PASS：脚本不理解物理，不证明评审独立，也无法防止作者编造复核；真实性和语义须由实际读者核实。

证据锚点引用正文解释段落，不引用标题、图题或表格单元格中的零散标签。数据和公式仍可放表格，但正文需说明表中关系和结论。完整段落匹配仅提高定位可靠性，不能判断段落技术质量；同一句空话写得更长也不因此合格。

验收不能只运行教学样例或检查图数、标题、哈希。新增/改动生成链后，至少保留：合格具体方案、名词流程空壳、改色但内容仍空、过期复核、正文外补解释、箭头 defs 冒充几何、真实矩形电路/软件图不误判等回归情形。
