# TRIZ 职工创新 Skill：创新研究能力与报告质量优化方案

> 状态：**研究建议 / 待实施**，不代表功能已经开发、测试通过或发布。  
> 日期：2026-11-06  
> 适用仓库：`luchi2333/triz-worker-innovation-research`  
> 审阅基线：`main` 中的 `SKILL.md` 版本 2.9.0、`CHANGELOG.md` 的 Unreleased 记录、`references/technical-report-quality.md` 以及仓库 README。  
> 范围：提升 **研究创新质量** 和 **研究报告的可信度与可读性**；维持 G0–G5 主流程、G1.5 人工确认、确定性矩阵、F/M/S/H 证据标记、现有安全硬闸门和自包含安装原则。

## 一、核心结论

现有 Skill 的突出能力是把现场问题贯通为“问题—矛盾—机理—查新—方案—风险—试验—效益—报告”，并以 `research-record.json`、确定性矩阵、工程一致性检查、报告内容复核和 DOCX 交付校验降低编造和前后矛盾。现有 `triz-extended-tools.md` 已涉及物理矛盾、物—场分析、标准解、演化与裁剪；`technical-report-quality.md` 已要求具体设计、算例、独立读者复核和创新归属，因此**不应把这些已有能力当作缺失功能重新开发**。

下一步最值得投入的是建立独立于格式与结构校验的**研究效果评估闭环**：

1. 衡量“现场语言 → 因果矛盾 → TRIZ 参数 → 可验证作用机制”是否推导准确。
2. 衡量 Skill 相比裸模型或普通 TRIZ 提示，是否实际产出更有价值、更可行、更经得起反证的创新方案。
3. 衡量每条关键报告结论是否被**恰当证据**支持，试验设计是否足以证伪，结果的不确定性是否清楚传达。

建议先做小规模、低依赖的评估试点；证实收益后再把新检查纳入强制门。现有 `validate_skill.py --strict`、`validate_deliverables.py --strict` 继续负责确定性的合同校验；未来 `evals/` 单独负责需要人工评审的概率性效果指标，两类结果不得合并为一个 PASS。

## 四、优先级与实施范围

### P0-1：建立最小可用 TRIZ-Worker-Bench（先试点，不预设大规模数据集）

**要解决的具体问题**：当前自动化回归能证明矩阵、结构、交付文件按规则生成，但不能证明创新成果优于基线。

**建议首批试点**：12–20 道脱敏或公开工程题，覆盖机械工装、电气/测量、工艺/作业；每题包含真实问题表述、系统边界、明确硬约束、可接受矛盾映射（允许多解）、反例与不可接受错误。涉及电网现场的题目全部采用虚构设备/离线研究场景，不导入敏感图纸、运行数据、保护定值或现场实施指令。

**三组对照**：A 裸模型；B 普通 TRIZ Prompt；C 当前 Skill。尽量保持输入、模型和可用工具一致，记录耗时、token、检索次数；输出匿名、随机呈现，至少两名独立评委评分，分歧较大时复核。每题优先采用配对比较，防止题目难易程度干扰结果。先冻结题目和评分规程，再运行；调提示的开发集与最终留出题严格隔离。

**评估维度（每项 0–4 分并附可查原句）**：

- 真实问题和硬约束保真程度；
- 矛盾方向/参数映射合理性；
- 方案作用机制可解释和技术差异；
- 新颖性主张的适度性与对最接近先例的解释；
- 工程可行性、失效链、可证伪试验；
- 报告的证据支持、复算和决策可读性。

**硬门槛**：虚构实测、虚构来源、错误将试验计划写成已验证、无依据宣称现场安全或越过用户确认，单独统计为关键错误。无论总分多高，含关键错误的输出都不能判为合格成果。

**首轮报告**：逐题 A/B/C 分数、双评委一致性（如加权 Kappa/ICC，按量表性质选）、差异分布、paired effect/区间、费用与耗时；小样本只说明探索性趋势，不写“显著优于所有基线”。若 12–20 题没有方向性收益，优先审查评分、触发和方案质量，不扩大数据集。

**建议新增（待实施）**：
- `evals/worker-bench/README.md`：语料边界、盲评协议、标注口径；
- `evals/worker-bench/cases/*.json`：题目及人审可接受标签；
- `evals/worker-bench/rubric.md`：0–4 分锚点、关键错误与争议处理；
- `evals/worker-bench/results/`：匿名原始评分、成本和统计报告。

**完成标准**：试点病例可复跑；评估表无身份泄露/结果顺序偏差；提交第一份包含负例的基线比较报告；至少指出一处因 Skill 规则导致的可复现优势或失误。正式 30–100 题扩充只有在试点证明值得投入时再启动。

### P0-2：独立评估“现场语言 → TRIZ 参数/方向”

**具体失效模式**：矩阵查得再准确，只要“欲改善”和“随之恶化”的参数映射错了，后续发明原理和方案都会偏离问题。

**最小方法**：让研究 Agent 在查询矩阵前输出机器可读的候选映射卡：
- `improving_parameter_candidates`、`worsening_parameter_candidates`：编号、中文名、对应原始证据句；
- `control_variable`、`change_direction`、`benefit`、`deterioration`、`causal_basis`；
- `confidence` 和 `needs_human_review`；
- 若不存在可证实的技术矛盾，允许 `no_triz_contradiction`、`assumption_only` 或 `reframe_required`，不得为了通过考核强行查矩阵。

先存为评估 sidecar，不立即改变 `research-record.json` 稳定 schema。按人工多标签金标计算：方向颠倒率、参数 Top-1/Top-3、参数对 precision/recall/F1、合理拒答率和误强制映射率。人工金标允许多个合理解释并保存分歧，不把单一标注员偏好当客观真理。

**验收**：在冻结的留出题上对比现有流程与候选映射卡；无新增方向颠倒，且其他指标出现有解释的改善才考虑纳入 G1；无改善则保留现状。

### P0-3：报告“主张—证据”支持度审计（从最小版本开始）

现有 F/M/S/H、来源卡、`report-quality-review.json` 和 `innovation_attribution` 已提供结构基础。无需建设新的图数据库；先在报告审查时生成一张**关键主张索引表**，记录：

| 字段 | 含义 |
| --- | --- |
| `claim_id` / `report_anchor` | 正文具体段落、图表或结论定位 |
| `claim_text` / `claim_strength` | 原文和主张强度（设计设想/来源显示/实测支持等） |
| `evidence_ids` / `evidence_class` | 既有 source/test ID 及 F/M/S/H |
| `supports_claim` | 支持 / 部分支持 / 不支持 / 无法核验 |
| `scope_limit` | 来源对象、工况、版本、样本等边界 |
| `action` | 降级措辞、补查资料、补做实验、删除结论 |

优先检查结论、摘要中的效益数字、创新性/新颖性、安全性、适配性及成熟度主张。`DOI`、专利号、标准编号仅作来源身份线索；**来源存在 ≠ 支持主张**。对摘要页面的关键句设 100% 人工支持度复核作为初始流程要求，不把“自动访问成功”计为已核实。

**验收**：公开教学/脱敏样例中，注入“来源仅证明部件、报告却声称整机达到 V3”“无 M 却写提升 30%”“专利摘要被写成首创证明”等负例，必须拦截或显式降级。审计单独报告证据状态，不冒称自动语义校验百分之百准确。

### P1-1：条件化的试验设计与统计附录

在现有 G4 验证协议上增加一份 **`references/experimental-design-and-statistics.md`**（待实施），**只有当课题涉及可重复测量或对比效果主张时**启动，不强制所有方向稿执行统计测试。

需要说明：
1. 基准对象、相同工况、对照/配对原则、样本单位与样本量选择理由；
2. 随机化/顺序平衡是否可行；重复测量是否属于同一个独立试样；
3. 量具/传感器校准与重复性，必要时进行 MSA/Gage R&R；环境和操作者变异；
4. 指标分母、原始数据文件、缺失值、异常值排除规则（试验前冻结）、停止/安全退出条件；
5. 效果大小与不确定性（均值差、百分比改善、置信区间或合适的非参数区间），避免只用“提高 X%”；
6. 效益计算的敏感性和边界情景，区分 H 预测和 M 观测。

没有样本时，输出**待验证协议**，不生成伪造的统计显著性。只有具备适当样本且方法成立时才计算区间。电气安全或人身安全场景的试验边界仍由现场合规/专业人员批准，本 Skill 无现场放行权。

### P1-2：报告按读者分层，但不增加重复写作

当前十章主报告、技术附件及 2–3 页决策摘要保留不动。根据任务用途**复用同一结构化研究记录**生成两种可选阅读入口：

- **职工创新评奖/答辩**：第一页呈现“现场痛点、推荐原理图、与现有方法差别、能解决的难点、已证实/待验证、价值”；附完整技术支撑，突出评委最关心的“为什么创新、方案如何工作、证据到哪一步”。
- **工程研究/技术审查**：优先“问题和边界—可对比基准—机理—实验—不确定性—风险—可复现附件”。

两者均不得替换现有 G5 正式报告或降低质量闸门。禁用空泛的“创新性显著、推广价值巨大”等无证据结语。优先利用 `final-report-blueprint.md` / `output-templates.md` 的可选速览路径，而不是引入第二套文档渲染引擎。

### P1-3：轻量运行可复现清单

先在当前记录/交付清单旁保存 `run-manifest.json`（仅在运行环境提供元数据时记录），字段建议：Skill commit、模型/版本（可用时）、日期、研究输入哈希、检索式及时间、source ID、主要脚本版本和人工修正记录。无法取得的字段明确写 `unavailable`，不伪造模型 temperature、隐藏提示或检索快照。

与现有 `research-record.json` 和 `deliverables-manifest.json` 做引用，避免复制大型事实内容或创建相互矛盾的第二事实源。仅在确实影响研究复现的问题中加入新的必填项。

### P2：收益成立后再开展的扩展

- **条件式 TRIZ 深化**：对物理矛盾/物—场/ARIZ 等已提供的扩展能力，先在 benchmark 检查是否选对方法、是否漏用；确认特定复杂题型有提升空间后，再加强条件路由或案例，不默认要求每题全跑。
- **三类端到端案例**：机械工装、电气/测量、作业工艺各至少一例，来源可核验、有试验协议、有限或真实数据及最终报告；企业案例须先脱敏、检查保密和权利归属。公开案例缺 M 则只发布研究设计，不宣称实际成效。
- **消融实验**：分别移除 F/M/S/H、G1.5 方向核对、反证、报告质量闸门，看收益、成本和失误率如何变化。每次只变一个组件，记录为何保留或删除，避免 Skill 无限制膨胀。
- **检索源适配器**：只有在跨宿主检索质量成为实测瓶颈后，再考虑 Crossref/OpenAlex、专利来源等可选入口；宿主检索能完成时不引入新强制依赖。

## 六、试点场景：单双屏蔽电缆开剥工具（示意，不含现场数据）

**输入样例**：开剥操作希望更快、更稳定，同时限制对屏蔽层和内层的非预期损伤；具体材料、结构尺寸、环境限制和现有工具必须另行核实。该示例只用于脱敏研究流程测试，不表示任何现场方案已被验证。

**预期研究输出**：

1. 保留原始工作步骤、刀具/导向/定位/被加工层的作用关系、伤害与损伤边界；
2. 构造“某操作变量变化 → 效率获益 → 损伤风险增加”的可证伪因果卡，列出多组可能的 TRIZ 参数映射及不确定性，不预先指定唯一标准参数号；
3. 比较成熟现有工具、限位/导向构思、可更换作用部件或其他跨领域机制；对每项分别写明“成熟技术来源、具体创新差异、待证实部分”；
4. 每条路线给出核心接触/运动机理图、失效路径、止挡/保护边界、材料兼容性验证、最不利工况；
5. 定义对照：同工况、同材料批次、同操作者或顺序平衡；记录单次操作时间、损伤定义与判定、返工率、培训/更换成本；
6. 报告中的结果按 F/M/S/H 分级；未实施试验则仅输出“研究方案与验证计划”，不写已提升百分比或可推广结论。

**评委盲评检查点**：同一份输出即使省略所有 TRIZ 编号，读者是否仍能说清原理？与最接近的成熟方案有什么结构或作用差异？什么观测会推翻推荐？没有这些信息的高分文案应被退回。

## 七、量化验收与停止条件

| 指标 | 度量口径 | 试点通过判据（建议，须预注册） |
| --- | --- | --- |
| 参数方向错误率 | 方向颠倒案例/可判方向案例 | 相对当前 Skill 不增加；关键工程题目标 0 |
| 参数映射 Top-1/Top-3 | 人工多标签金标一致率 | 报告基线与变化，先看改善趋势，不预设虚假成功数值 |
| 技术方案质量 | 双评委的盲评配对差异和分项分布 | Skill 相对两组对照有实际可解释收益；差异为零时不扩大开发 |
| 引用支持度 | 关键主张有可定位、范围相符证据的比例 | 决策摘要关键主张逐条复核；不支持项全部降级或删除 |
| 关键错误数 | 伪造 M/来源、越权安全声称、错误提升成熟度等 | 正式成果容忍 0；评估时披露所有出现次数 |
| 可重复性 | 独立读者按报告重算、复现实验步骤的成功情况 | 至少两名复核者能指出数据入口、计算中间量、失效反例 |
| 报告可读性 | 首次阅读能否复述问题、方案、差异和证据成熟度 | 盲评记录错误理解与修改建议，复审后再定门槛 |
| 成本和耗时 | 每题 token/外部检索/人工分钟/总耗时 | 与质量增益同时报告；质量没有提升则不接受持续复杂化 |
| 既有合同回归 | strict、矩阵、DOCX、工程图、负测 | 全部现有回归保持通过；失败先定位原因 |

**提前停止**：出现无法安全脱敏的数据需求、评估者无法就评分规则达成基本一致、改动显著增加维护成本却没有复现性质量增益，或新规则造成正常流程大量误拦截时，先停止推广并回退可选功能。极端安全假设不用于泛化扩展开发，除非有现实故障证据和可衡量收益。

## 八、建议实施顺序和工作量边界

1. **先记录基线**：保存当前 main commit、strict/矩阵/报告自测结果和可公开的 12–20 题试点集合；不碰发布版本号。
2. **先评估再改提示词**：跑 A/B/C 匿名盲评，定位低分案例究竟出在事实保真、参数映射、检索归属、方案机理还是报告论证。
3. **只修最多两类高频问题**：例如参数映射卡、主张证据索引；新增内容通过条件加载或评估 sidecar，不把完整统计/评估材料灌入每次 G0。
4. **留出集回归**：相同模型、相同测试输入、固定评价口径进行对照，公开负结果及成本；确认收益后再正式修改主链。
5. **最后补报告细化**：试验统计和读者摘要问题优先由现有 G4/G5 文档扩充解决；仍不足再增加脚本。
